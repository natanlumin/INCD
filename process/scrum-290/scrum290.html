Assessment tooling for open-source models: a desk survey and comparison

What this document answers

An organisation that takes an open-source model (SCRUM-281) into use meets it in two states, and in each it needs tools.

  • Before adoption: the file (SCRUM-281) is in hand.
    • The organisation can read the file without running it: scan its format for code that runs on load, and check that it is the file the producer (SCRUM-281) published.
    • It can run the file and test it: send it inputs and judge the outputs, or read its internals while it runs, looking for what no metadata shows.
  • In service: the model answers requests.
    • Guards sit in front of and behind the model and decide what reaches it and what leaves it.
    • Monitors read what arrives and what is returned, and the same tests are run again to see whether the model in service still gives the outputs it gave when it was assessed.
  • Many tools exist, and they are not alike.
    • They differ in what they cover, in the access they need, in how far their maintainers stand behind them, and in what their licences allow.
    • Some that are still cited are no longer maintained. Some that are cited in research have no licence at all.

This document surveys the tools in each state and compares them on one table. It is a desk survey: every statement about a tool comes from the tool's own documentation or release record, and no tool was run.

Part 1. Categories, placement and the five comparison dimensions

1.1 The categories

The survey covers six categories of tool.

  • Artefact and format scanners read statically, without loading or running anything, for code that would run when the model is loaded. Three objects are read, at different stages: the file alone, the code shipped with it, and the packages that code brings in; 2.1 takes them in turn.
  • Red-team and adversarial frameworks send inputs to the model and judge what comes back, or perturb inputs to change a prediction.
  • Guardrail layers are guards (SCRUM-281): controls (SCRUM-281) placed in front of or behind the model in service. They are not the model's safeguard (SCRUM-281), the refusal behaviour its publisher trained into the file: the safeguard is not a category of tool but a property the tools assess, set out in 2.3.
  • Runtime monitors read the inputs that arrive and the outputs returned while the model is in service.
  • Provenance verifiers check a signature, an attestation or a hash, so that the file in use can be shown to be the one published, by the one who published it.
  • White-box analysis: tools that read the model's internals, its weights and activations while it runs, rather than its file format or its outputs. Their ground is mechanistic interpretability, "reverse engineering the computational mechanisms and representations learned by neural networks into human-understandable algorithms and concepts" (Bereska and Gavves, TMLR 2024) [TL-48]. Two uses matter here: looking for a hidden trigger, by inverting the model's behaviour (T10; D2), and finding the mechanism that carries the safeguard, such as the refusal direction (Arditi et al., NeurIPS 2024) [TH‑17]. White-box analysis holds the only tools that read for backdoors and trojan triggers, and the only way to check the safeguard from inside the model; without it T10 would have no row, and Q2.3 only half of one.

1.2 Where each category works

The lifecycle stages (SCRUM-281) are four: S1 selection, S2 adjustment, S3 deployment and S4 runtime detection, labelled as in the lifecycle assessment framework (SCRUM-284, stage tables, notation). Each holds evidence items, written en.k for the k-th item of stage n, and questions, written Qn.k.

The test families are four, named in the glossary (SCRUM-281, section 1.4) and each defined by the evidence kind it reads (SCRUM-284, section 1.1, Table 1):

  • static reads what is readable in the file or the deployment, without running the model;
  • dynamic reads the model's internals while it runs, white-box, so it needs the file;
  • behavioural reads the model's outputs on chosen inputs, black-box, so it works in possession and by proxy;
  • provenance reads what the platform guarantees: account, upload date, hashes, gating.

A tool reads one evidence kind, and it can be used at every lifecycle stage whose evidence includes that kind, where its access need is met (SCRUM-284, section 1.4). The lifecycle assessment framework placed the tooling kinds by this rule before any tool was named (SCRUM-284, stage tables, section M); Table 2 repeats that placement, and Part 3 places each tool by it. The text of every question and evidence item is in the annex, Table 12.

1.3 The five comparison dimensions

Each tool is compared on the five comparison dimensions the survey is asked for. Each dimension has a fixed meaning and, where it is graded, a fixed scale.

  • Coverage. The threats the tool reads for, by number, T1 to T21; the testable properties, D1 to D5, and the attestable ones, P1 to P6, where it reads one; and the rows of the segmentation it addresses, classification, embedding or generative, the model-type axis (SCRUM-281, section 1.2, Axis A) as segmented in SCRUM-280, Table 4. A tool covers a threat where its own documentation names the threat or the technique; a claim of the maintainer that has not been tested independently is marked emerging (SCRUM-281).
  • Lifecycle stage. The stages S1 to S4 at which the tool can be used, by the rule of 1.2 and the access the tool needs.
  • Maturity. How far the maintainers stand behind the tool, read from published markers only, not from any judgement of quality. Five grades:
    • stable: a release at version 1.0 or above, or a stated "Production/Stable" status, and maintained;
    • pre-release: a stated alpha or beta status, or a version below 1.0, and maintained;
    • research code: code published with a paper, with no release process;
    • dormant: no change in the year before the evaluation date, and not archived;
    • retired: archived, or stated by its maintainers to be no longer maintained. A stated status takes precedence over a version number: a tool at 1.2 that states "Alpha" is graded pre-release.
  • Licensing. The licence of the code, by its SPDX identifier, read from the licence file; the licence of any model the tool ships, where it differs; or the absence of a licence. Without a licence, the default copyright laws apply and "no one may reproduce, distribute, or create derivative works" from the code (GitHub, licensing a repository) [TL-34].
  • Operational fit. What the tool needs to run: the file alone, the weights loaded with their hardware, a running endpoint, keys or an identity; its interface, command line, library or continuous-integration step; and any dependency on a third-party service.

1.4 What a desk survey can and cannot say

  • It can say what the maintainers state: what the tool reads, how, with what access, under what licence, at what version and with what status. Each statement here is cited to the tool's documentation or release record, an Official source in the citation policy (SCRUM-281).
  • It cannot say how well a tool works. Detection rates, false-positive rates and resistance to evasion are stated here only where a research paper measured them, and cited to that paper.
  • Its versions have a date. The versions, licences and statuses in Table 9 are those published on the evaluation date stated in the table's caption. Tools change; the table is a record of that date, and the method of 1.3 is what lets it be repeated.

2.1 Artefact and format scanners

What a scanner reads has to be stated, because three different objects can be called "the model", and they enter at different stages and carry different threats.

  • The file alone. The weights container, the serialised objects inside it, its metadata and the templates stored with it. Reading it is file analysis: nothing outside the file is involved. It is readable at selection and after adjustment (e1.4, e2.1), and an own scan of it is e1.6. Malicious serialisation (T3), malicious adapters (T6) and the template part of T5 live here.
  • The code shipped with the file. Custom modelling code, Python files uploaded with the weights, which the loader runs only when the user allows it with trust_remote_code [SC‑08]: "the second path to code execution beside pickle" (SCRUM-284, stage tables, Q1.3). It is readable at selection (e1.4), but reading it is code analysis, not format analysis: the code part of T5.
  • What that code brings in. The third-party packages the shipped code imports, and the loader and serving software that run it: software during loading (T8). It is first in hand when the organisation builds the environment or container that will run the model, read at deployment (e3.3), where "the object scanned is the container or engine contents, not the file alone" (SCRUM-284, stage tables, section M), and re-read in service (e4.1).

The category is surveyed in the same three groups. The first group is made for model files. The second and third are general software tools: they read Python code, packages and containers wherever these come from, and none of their READMEs mentions model files [TL-35 to TL-42]. They are included because the lifecycle assessment framework places code and container scanning in this category (SCRUM-284, stage tables, section M), and because without them the code part of T5 and all of T8 would have no tool.

The file alone.

  • picklescan lists the globals a pickle imports and checks them against lists of safe and unsafe imports; it reads pickle files, PyTorch archives and NumPy files, from local paths, URLs or Hugging Face repositories, and returns an exit code for use in a pipeline (picklescan, README and source) [TL-01]. It is the scanner the Hugging Face Hub's pickle scan builds on, and it has had published bypasses: an installer call missing from its unsafe list [SC‑15], and a parsing flaw that its maintainer states "also affects the online hugging face pickle scanners" [SC‑16].
  • ModelScan "currently supports: H5, Pickle, and SavedModel formats" and "reads the content of the file one byte at a time just like a string, looking for code signatures that are unsafe"; it ranks findings in four severities and is designed for continuous-integration use (Protect AI, ModelScan README) [TL-02; SC‑26]. It does not list GGUF, ONNX or safetensors.
  • fickling is a "decompiler, static analyzer, and bytecode rewriter for Python pickle" that executes the pickle symbolically rather than running it, and can hook the loader at run time with an allow-list of imports from machine-learning libraries; imports the user adds to the list are trusted (Trail of Bits, fickling README) [TL-03].
  • ModelAudit registers scanners across model, archive and configuration formats, among them pickle, PyTorch, safetensors, GGUF, ONNX, Keras, SavedModel and chat templates, without loading or executing the model, and can emit a CycloneDX bill of materials (Promptfoo, ModelAudit README) [TL-04]. It also reports "potential backdoor indicators" from suspicious weight patterns and anomalous tensors [TL-04]; that is a claim of the maintainer, not independently tested: emerging. Its security model states the limit plainly: a clean scan means "no known indicators were found," not "risk is zero," and "runtime-only backdoors and environment-triggered logic may not be visible" [TL-05]. Packaged installs enable telemetry by default [TL-04]. Of the shipped files it reads the chat templates; its documentation does not state that it analyses shipped Python modelling code [TL-04].
  • The Hub's own scans are platform-side controls (SCRUM-281), not tools an organisation adopts: ClamAV on every file and a pickle-import scan on every pickled upload [HF‑05, HF‑06], and the Protect AI and JFrog scanners on public repositories [HF‑07, HF‑08]. The Hub states that its lists are kept "in a best-effort manner" and that the scan "is not 100% foolproof" [HF‑06]. Shipped code is reached only by the antivirus signatures; to the Hub it is an ordinary file (supply-chain document, Table 4, row T5).

The code shipped with the file.

  • Bandit "is a tool designed to find common security issues in Python code": it "processes each file, builds an AST from it, and runs appropriate plugins against the AST nodes" (PyCQA, Bandit README) [TL-35]. It reads the shipped modelling code as it reads any Python file, statically and file by file.
  • Semgrep Community Edition is a static analysis tool for 30 or more languages, driven by rules from a registry; its maintainers state that "in security contexts, Semgrep Community Edition will miss many true positives as it can only analyze code within the boundaries of a single function or file", and that using registry rules "reports pseudonymous rule metrics to semgrep.dev" unless switched off (Semgrep, README) [TL-36]. Its licence is LGPL-2.1 [TL-36].
  • GuardDog "identifies malicious PyPI and npm packages" and packages of other registries; it "runs static analysis on package source code (through YARA rules)" and correlates what code can do with threat indicators, because indicators alone "might be false positives"; it scans a registry package, a local archive or directory, or every package in a requirements file (Datadog, GuardDog README) [TL-37]. It is the one tool here that reads for intent, malicious code, rather than for flaws.

What that code brings in.

  • pip-audit scans "Python environments for packages with known vulnerabilities" from the Python Packaging Advisory Database, an environment or a requirements file; its security model states that it "is not a static code analyzer. It analyzes dependency trees, not code", and "If you wouldn't pip install it, you should not pip audit it" (PyPA, pip-audit README) [TL-38].
  • OSV-Scanner finds "existing vulnerabilities affecting your project's dependencies" from lockfiles and manifests and in container images, against the OSV database; its README describes its current version as beta (Google, OSV-Scanner README) [TL-39].
  • Syft generates "a Software Bill of Materials (SBOM) from container images and filesystems" in CycloneDX or SPDX, and can sign it as an in-toto attestation; Grype scans "container images, filesystems, and SBOMs for known vulnerabilities" (Anchore, READMEs) [TL-40, TL-41]. Together they inventory the container in which a model is served and match it against known vulnerabilities.
  • Trivy scans container images, filesystems, repositories and clusters for vulnerabilities, misconfigurations, secrets and licences, and produces a bill of materials (Aqua Security, README) [TL-42]. Its maintainers' advisory records that a threat actor "used compromised credentials to publish a malicious Trivy v0.69.4 release" and malicious images (Aqua Security, GHSA-69fq-xp46-6x23) [TL-43]: an assessment tool is itself software in the supply chain, and the same provenance checks apply to it.

What the category cannot do.

  • File scanners read code paths, not behaviour. They read what runs on load, not what the weights do. A research evaluation found the scanners it tested missed known malicious models (Kellas et al., ACM CCS 2025) [SC‑18]. No scanner in this survey reads for a parser exploit in a weight format (T4) by name.
  • Code scanners do not know they are reading model code. They find patterns and known flaws in Python files; none states a rule for what modelling code should or should not do [TL-35 to TL-37].
  • Dependency scanners report known vulnerabilities, not intent. A package without a published advisory passes pip-audit, OSV-Scanner, Grype and Trivy; only GuardDog reads package code for malicious behaviour [TL-37, TL-38].
  • The import chain is not resolved from the file. No tool here starts from a model repository and follows what its shipped code imports. The packages are known only once an environment or container is built, which is why the third object is read at deployment (e3.3), not at selection.

  • promptfoo in red-team mode tests applications, retrieval pipelines and agents for indirect prompt injection, leaks of personal data from context and "misuse of connected APIs or databases (in agents)", through an HTTP API, a browser or direct model access, configured in YAML (promptfoo, red-team documentation) [TL-13]. Its README states "Promptfoo is now part of OpenAI. Promptfoo remains open source and MIT licensed." [TL-13].
  • Inspect is "a framework for large language model evaluations created by the UK AI Security Institute" (Inspect README) [TL-14]. It also offers a guard mode [TL-16].
  • AgentDojo is "a dynamic environment to evaluate prompt injection attacks and defenses for LLM agents" (ETH Zurich and Invariant Labs, AgentDojo README) [TL-21]; its benchmark is the research result cited for indirect injection against agents (Debenedetti et al., NeurIPS 2024) [TH‑51]. Its maintainers state that "the API of the package is still under development and might change" [TL-21].
  • Adversarial Robustness Toolbox (ART) implements "Evasion, Poisoning, Extraction, and Inference" attacks for classification, object detection, speech recognition and generation, across TensorFlow, PyTorch, scikit-learn and others, under the Linux Foundation AI & Data Foundation (ART README) [TL-17]. It is the only maintained tool here that reads for model extraction (T18) and membership inference (T20), and for poisoning (T9) on the classification row. Its documentation does not name large language models [TL-17]. Some of its attacks need the model object, white-box, and so the file [TL-17].
  • TextAttack runs "adversarial attacks, data augmentation, and model training in NLP" on classification and sequence-to-sequence models loaded in process, including gradient-based search (TextAttack README and documentation) [TL-18]: robustness (D4) on the classification row.
  • HarmBench is a benchmark "for evaluating automated red teaming methods and LLM attacks/defenses", with behaviours, attack methods and judge classifiers (Center for AI Safety, HarmBench README) [TL-19]. It has no release, and no change in the year before the evaluation date [TL-19].
  • Counterfit brought "several existing adversarial frameworks under one tool" for classical models; its repository is archived and names no successor (Microsoft, Counterfit) [TL-20].

What the category cannot do. A red-team result is a judgement of outputs on chosen inputs; it finds a trigger only if an input happens to contain it, and its verdicts are as good as the judge that scores them, which several of these frameworks delegate to another model [TL-16, TL-19]. No framework here reads for quantisation drift (T12), quantisation-triggered backdoors (T13) or merge contamination (T14) by name; each can be pointed at the changed file and compared with the base, which is the measurement chain of the lifecycle assessment framework (e1.9, e2.5), not a feature of any tool.

2.3 Guardrail layers

A guard (SCRUM-281) is a control (SCRUM-281) assessed with the model, not a method that assesses it (SCRUM-284, section 1.4). The survey compares guards because the organisation chooses one, and the choice is set at S3 (e3.3) and measured through the behaviour of the deployed system (e3.5, e4.3).

A guard is not the safeguard (SCRUM-281). The glossary separates the two: the safeguard is "the model's own refusal behaviour, trained in by its publisher, inside the file"; a guard is "a control placed around the model, in front of or behind it", and the word "guardrail" is not used for the model's own refusal (SCRUM-281, section 1.3). The safeguard is therefore not surveyed here as a category. It is a property the tools assess, at two questions of the lifecycle assessment framework: whether it is present at selection (Q1.6) and whether it is still present after an adjustment (Q2.3), where fine-tuning, adapters, quantisation and merging can weaken it (T11, T12, T14) and an abliterated model (SCRUM-281) has had it removed on purpose. Two kinds of tool read it:

  • From outputs, the red-team frameworks of 2.2, which measure whether the model refuses (e1.9, e2.5).
  • From internals, the white-box tools of 2.6, which look for the refusal mechanism itself, the direction in the model's activations that mediates refusal (Arditi et al., NeurIPS 2024) [TH‑17] (e1.10, e2.4).

A guard can stand in for a weak safeguard in service; it cannot show that the safeguard is there.

A scanner gives a statistical verdict with an error rate, not proof that no trigger is present (threats document, T10).

Summary: the five questions answered

The survey is desk-based: every statement about a tool is taken from the tool's own documentation or release record, and no tool was run (1.4).

  • Which kinds of tool exist, and where does each work? Six categories: the five the survey is asked for, artefact and format scanners, red-team and adversarial frameworks, guardrail layers, runtime monitors and provenance verifiers, and white-box analysis, which holds the only tools that read a model's internals for hidden triggers. Each is placed on the lifecycle stages by the evidence it reads (Table 2).
    • Red-team frameworks are the only category that works at every stage, S1 to S4, and by proxy.
    • Runtime monitors work at S4.
    • Scanners work at S1 to S3, on the file, the shipped code, or the packages and container; the package scanners re-read at S4.
    • White-box tools need the file and the hardware to run it, and work at S1 and S2.
    • Provenance verifiers anchor at S1 and re-read at S2 to S4.
    • Guardrail layers are controls, assessed with the model at S3 and watched at S4, not methods.
  • What does each tool cover, and what does it need? Part 2, one table per category, Tables 3 to 8: for each tool what it reads, its method and the access it needs, each cited to the tool's own documentation. Each category closes with what it cannot do.
  • How do the tools compare? Table 9 compares every tool surveyed on the five comparison dimensions, coverage, lifecycle stage, maturity, licensing and operational fit, with the version of each tool as published on the evaluation date, 18 November 2026.
    • Maturity is low: most maintained tools state an alpha or beta status or sit below version 1.0.
    • Licences are permissive, mostly MIT and Apache-2.0, where code is maintained. Two of the four white-box tools, BAIT and PICCOLO, carry no licence and cannot be adopted as published.
    • Operational fit divides by access: the file, the shipped code, the built environment, or an endpoint.
  • What does no tool cover? Four gaps (Table 10): the model-integrity threats have no adoptable tool; the embedding row has no tool; runtime monitoring has no maintained dedicated tool; and the safeguard can be checked from outputs only.
  • Which tools should the demonstration set use? Eleven: ModelAudit, picklescan, Bandit, GuardDog, pip-audit, model-signing, garak, PyRIT, AgentDojo, ART and LlamaFirewall. Each is justified from its row of Table 9 against four stated conditions (Table 11), and every tool not proposed is listed with the condition it fails. Two demonstrations have no adoptable tool:
    • hidden triggers (T10): BAIT and PICCOLO are unlicensed research code, so the demonstration rests on a technique reimplemented from the published paper, or on a licence obtained from the authors;
    • the safeguard read from internals (Q2.3): refusal_direction is dormant research code, so the check is reimplemented from its paper [TH‑17].
